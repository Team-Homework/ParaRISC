# 双发射端口预算与超额请求规则

> 这是 ParaRisc **宽度 2 性能配置**的已选资源预算，A/B 在 G0 将它落实为共享参数与接口。宽度 1 保留为功能基线。本文的“端口”指每拍可独立接受的逻辑访问，不能直接等同于工艺库现成的 SRAM 宏；唯一待课程接口确认的是统一下级内存的实际协议与可重叠请求数。
>
> 目标：在连续 Cache 命中、两条独立整数指令充足时，电路具备稳定每拍发射和提交两条的能力；正式 Benchmark 是否达到 **IPC > 1** 及当前 100 分档的 **IPC ≥ 1.0140**，须在课程的统一内存、20 周期延迟和正式统计口径下实测。

配套：[项目约束](../README.md) · [A/B 分工](project-ab-plan.md) · [硬件结构设计](cpu-hardware-design-guide.md)。

## 1. 先统一“端口”是什么意思

| 名称 | 例如“2”的含义 | 不是这个意思 |
| --- | --- | --- |
| 请求/响应带宽 | 一拍最多 `fire` 两笔事务 | 每笔事务只延迟两拍 |
| 存储阵列读口 | 一拍能用两个独立地址读数据 | 必然有两块独立存储器 |
| 存储阵列写口 | 一拍能在两个独立地址更新数据 | 两条 Chisel 赋值自动合成一个物理口 |
| 宽字读口 | 一次读 256 位 Cache 行，再选两个 32 位字 | 256 个独立读口 |
| 提交口 | 一拍确认两条最老且已完成指令 | 任意两条已完成指令都可提交 |

**延迟、每拍吞吐和最大在途数分开记录。** 如除法器一笔运算用约 32 次迭代，不代表每拍能接新除法；流水乘法可有多拍延迟但每拍启动一笔。下表的数组端口是拟实现组织，并非声称目标工艺一定有对应的多端口宏。[Chisel 存储器端口与时序说明](https://www.chisel-lang.org/docs/explanations/memories)

## 2. 宽度 2 的具体预算

初版用 `issueWidth=2、commitWidth=2、fetchWidth=2`；ROB 24 项、PRF 64 项、RS 12 项、前端到后端输入缓冲 4 条、已提交 Store Buffer 8 项可作为**测量起点**，容量不是已经证明的最优参数。先固定下表逻辑带宽，再由面积和关键路径决定是否改成银行化或多拍访问。

| 部件/方向 | 每拍预算 | 超额时由谁处理 | 何时算已接收 |
| --- | --- | --- | --- |
| I-cache → 前端 | 命中时 **1 次整行宽读取**，选出至多 2 条 32 位指令 | 跨行只给第 1 条；miss 阻塞本 Cache 新访问，前端靠缓冲继续供给 | 取指响应 `fire` |
| 预测表 | 每拍最多 **2 个候选 PC 查询、1 项训练写入**；训练队列可同拍入 2 项 | 提交遇两条分支时先入训练队列；队列满则限制相应提交，不能丢训练事件 | 查表与训练队列入队分别计数 |
| 前端 → Backend | 每拍 **1 个包，含 1～2 条**；Backend 缓冲一拍最多入 2、出 2 | 输入缓冲满则反压整个包；包内后续逐条处理 | 整包 `fire`，每条只入队一次 |
| 译码 | **2 条/拍**；预测/选择需检查两槽控制流 | 遇先出现的预测跳转，截掉同包更年轻槽；容量不足时前端保持包 | 有效包进入 Backend 缓冲 |
| RMT 投机映射 | 最多 **4 个源读、2 个目的旧映射读、2 个目的更新** | 第 2 条与第 1 条 RAW/WAW 用组内旁路；不足资源只处理缓冲中的连续前缀 | 指令完成重命名分派 |
| AMT 已提交映射 | **2 个映射更新/拍** | 同拍两条写同一架构寄存器时按顺序合并，较年轻版本生效 | 对应指令提交 |
| Free List | 最多 **2 个新物理寄存器分配、2 个旧寄存器归还** | 空闲数不够时只分派可完整接收的前缀；x0/无目的不分配 | 与 ROB/RS 等同拍分配成功 |
| ROB | **2 分配、2 完成写入、2 队首检查/提交** | 队首未完成或 store 提交资源不足时，提交 0/1 条；满则停止分派 | 分派、完成、提交分别以本域确定的事件计数 |
| RS | **2 入队、最多 2 出队**；2 路完成标签唤醒 | 两路选中不同条目且符合单元类型；未被执行器接受者留在 RS | 执行请求 `fire` |
| LSQ | **2 条访存元信息入队、1 个地址生成、1 笔数据事务/拍** | 同包两条访存都可分配槽位，但只有一路 AGU/数据口；若容量不够只收连续前缀 | 分配与 D 请求分别计数 |
| PRF | **4 个源数据读、2 个结果写**；p0 恒为零 | 读/写同拍相关值走明确旁路；超过写口的结果留在完成缓冲 | 获得写回口的完成事件 |
| 整数执行 | **2 路普通 ALU**，其中一路支持 Branch | 两条 ALU 可同拍发射；Branch 抢有分支能力的通道，其他候选重新选择 | 对应执行单元请求 `fire` |
| 地址生成 | **1 路 AGU/拍** | 第 2 条待计算访存保留在 RS/LSQ；已提交 store 排队，不能伪造第二个 Cache 口 | AGU 请求 `fire` |
| MDU | **1 个请求/拍**；乘法流水线目标 II=1；除法独立迭代单元 | 除法 busy 时拒收新除法，不阻断独立乘法；MDU 完成结果持有至接收 | MDU 请求和响应各自 `fire` |
| 完成/写回 | 所有来源合计 **2 条完成事件/拍**、最多 2 次 PRF 写 | ALU/Load/MDU/Branch/Store 各自保留未获准完成项；仲裁不得丢单拍脉冲 | 仲裁选中并写入 ROB/PRF 的事件 |
| 已提交 Store Buffer | **1 项提交进入/拍**，最多 1 项向 D 端口送出 | 双提交遇两条 Store 时本拍只提交连续前缀中的第 1 条；缓冲满阻塞队首 Store | 后端提交入缓冲；D 请求 `fire` 是另一事件 |
| D-cache CPU 口 | **1 个 32 位字事务/拍**（读或带 4 位 byte mask 的写） | 同拍 Load 和排空 Store 竞争时按序选一个；未选请求保持在 A 端 | D 请求 `fire` |
| D-cache 数据阵列 | 基线每 way **1 个行读或行写访问/拍**；Tag/元数据配套 | 同一阵列端口的命中读、store 更新、回填/写回不能任意并行；miss 期间 blocking | 阵列访问由 Cache 状态机仲裁 |
| I-cache 数据阵列 | 基线每 way **1 个行读或行写访问/拍** | 回填占用访问时暂停新查找；整行读后两个字选择器不增加阵列读口 | 阵列访问由 Cache 状态机仲裁 |
| Cache Tag/valid/dirty 元数据 | 每 way 至少 **1 次组查询、1 次被仲裁的更新/拍** | 查找、替换和回填涉及同组时按状态机顺序执行；不假设同址读写自动旁路 | 与数据阵列的行身份一同锁存 |
| 统一下级内存 | **按正式课程接口确定**；未确认前适配器按单在途、一次只发一笔做保守基线 | I/D 缺失和脏行写回在 B 的同一个仲裁器排队；不能假设 I/D 各有独立主存 | 正式接口定义的请求接受/响应完成事件 |

RMT 一拍为两条指令同时处理最多四个源寄存器；两个目的旧映射查询与两个新映射写入是另外的访问需求，不能把“4 读 2 写”直接照搬成 RMT 的全部端口数。对 RMT，旧目的可从同一架构寄存器的前馈链或现有读网络取值；落地时要明确综合出的读选择网络和优先级。LSQ 的分配宽度与 AGU 吞吐不同：前者让两条访存指令进入窗口，后者限制一拍实际算几个地址。

PRF 的 **4R2W** 是为两条双源指令不受普通端口冲突限制而选择的逻辑组织。第一版可用寄存器阵列、四路读选择和两路写使能描述，核对 Yosys 面积/时序后再选择银行化。多端口 PRF 和旁路的硬件代价可参看 [BOOM 寄存器堆/旁路说明](https://docs.boom-core.org/en/latest/sections/reg-file-bypass-network.html)。

统一内存只有“一份”已知，**物理端口数、读写响应细节与可重叠请求能力仍要由课程接口确认**；表中单在途是我们适配器的保守选择，不得写成课程规定。20 周期延迟不等于每 20 周期必可整行回填，行传输次数仍受下级数据宽度约束。

## 3. 超额请求的共同处理优先级

```text
候选请求 → 检查年龄与依赖 → 检查各部件本拍预算
         → 选最多 2 条合法指令 / 2 个完成结果
         → 只有 valid && ready 的请求才真正占用资源
         → 未获准者原地保持或进入有容量的缓冲，下一拍重试
```

对 A 的后端，先保证**老指令不会被年轻指令绕过提交**；发射阶段可以选就绪的年轻项，但写回端口冲突必须保存每个未获准的结果。固定优先级可能使慢单元饥饿，仲裁器需要等待计数或轮询等公平处理及相应测试。两条分派进入 ROB、RS、Free List 的接受数必须一致；它们不是三个可以分别说 ready 的独立交易。

对 B 的服务，I/D 对同一个下级请求口竞争，读/写/回填各有保存的位置。`req.valid` 在 `!req.ready` 时保持地址/数据不变；`resp.valid` 在 `!resp.ready` 时保持结果不变。同步存储器同址读写的默认读值不能当成新数据，所需同拍旁路由模块显式定义。[Chisel `SyncReadMem` 语义](https://www.chisel-lang.org/docs/explanations/memories)

### 3.1 双宽稳态的一次逐拍例子

```text
周期 T：    I-cache 命中，读出指令 a、b → 前端打包
周期 T+1：  Backend 缓冲接收包，内部可同时重命名 a、b
周期 T+2：  若 a、b 独立且都是 ALU，4 个源走 4R PRF，分别发给 ALU0/1
周期 T+3：  两个完成结果走 2 条写回通路，ROB 中两个 done 置位
周期 T+4：  ROB 队首两条已完成，同时提交；后一组沿同样流水重叠运行
```

表是按每级一拍的示意，真实排布可能增加寄存器或旁路，但**稳定状态下每拍仍需能重复接收下一组两条指令**。不能靠仅在单个周期“同拍完成两条”就宣称平均 IPC>1。

若 b 是 Load 且本拍数据口忙：a 可以继续，b 留在后端缓冲/RS；不能把 b 算作已发给 LSU。若两条同时完成而写回口只有 1 个，本方案必须把另一个结果保持，实际吞吐就会受限，因此预算选择 2 写回口。

## 4. 值得写在代码里的限制

| 位置 | 必须落实的约束 | 审查/测试方法 |
| --- | --- | --- |
| 生成参数 | `issueWidth=2` 时 PRF 读口数≥4、全局完成口≥2；ALU 可提供两条整数运算 | `require`/静态断言，宽度 1/2 两档分别生成 |
| 发射选择 | 同一 RS 条目不得被两口选中；每类单元实际请求≤预算 | 两路竞争、执行器 busy、类型冲突测试 |
| LSQ/AGU | 两条访存可入队，但每拍至多一个地址生成及一个 D 请求 | 同包双访存、老 store 未排空、D 口忙测试 |
| PRF | 同拍 2 写的数据和目的地址分别保存；禁止两个不同结果写同一物理号 | 同时 ALU+Load/MDU 返回测试 |
| ROB/Free List | 分派和提交只处理连续合法前缀，计数不超深度 | 满/空/回卷/同拍入出测试 |
| 前端缓冲 | 能整包接收 1/2 条，内部可消耗 0/1/2 条；重定向取消旧包 | 连续双包、背压、恢复同拍测试 |
| Cache 阵列 | 数据/Tag 的读写冲突规则和同步读取拍数明确 | 命中并发、回填与 CPU 请求争用测试 |
| 下级内存 | 所有 I/D/写回事务最终进入同一适配器 | I/D 同时 miss、脏写回和随机背压测试 |

`SyncReadMem.read`、`SyncReadMem.write` 每写一次就会描述相应端口；Scala `for` 访问数组也不会自动把几个硬件请求分摊到不同周期。若真实工艺只支持更少的端口，就必须改成银行化、复制只读部分、时分复用或增加流水级，然后重新测 IPC/面积/频率，不能仅改一个参数数字。

## 5. 让“IPC>1”从结构目标变成可验证结果

| 阶段 | 程序/条件 | 需要看到什么 | 证明范围 |
| --- | --- | --- | --- |
| 整数宽度诊断 | I-cache 命中、两条互不 RAW 依赖的整数指令不断供给；D/MDU 不参与 | 稳态重复出现每拍 2 分派、2 发射、2 完成、2 提交；诊断 IPC 明显 >1，建议先达到 1.5 | 验证双宽链路真实打通，不代表正式成绩 |
| 资源冲突诊断 | 混入双访存、乘法结果与 Load 同拍完成、D-cache 忙 | 超额者保持并最终完成；统计各端口冲突拍数 | 验证规则正确且能定位瓶颈 |
| 正式性能 | 规定 Benchmark、统一内存、20 周期延迟、课程统计区间 | 实测 IPC >1；当前高档还需 ≥1.0140 且面积、频率达标 | 才能判断项目目标是否达成 |

建议计数：`commit0/1/2` 拍数、双槽前端有效率、`rename2/issue2` 拍数、PRF 读/写冲突、写回等待、LSU/MDU busy、I/D miss、下级仲裁等待与恢复拍数。每次参数实验保存源码版本、配置和同条件结果。

从指标关系也能看出结构与实测的区别：若活动周期平均完成 `1+p` 条，零提交周期比例为 `s`，则该统计区间约有 `IPC=(1-s)(1+p)`。即使双提交硬件存在，miss/恢复造成的 `s` 过大，IPC 仍可能低于 1。这个式子是简化的计数分析，不替代实际流水仿真。

如果正式 IPC 未达标，先读计数器：前端不足则 B 检查 I-cache/预测/供给；PRF/RS/ROB 或结果口受限则 A 检查后端；D-cache miss 与统一内存争用则 B 检查缓存与仲裁，A 检查访存顺序和隐藏延迟的窗口容量。新增端口之前先确认瓶颈，并同时测面积与 300 MHz 时序。

这份预算固定了能**理论持续两条独立整数指令/拍**的必要通路和超额处理方式。正式 IPC、面积、频率无法由端口数单独保证；完成相应 RTL、工具链和 Benchmark 后，才能把目标写成已验证结果。
