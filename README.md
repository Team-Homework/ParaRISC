## 1. 我们要完成什么

**使用 Chisel 实现支持指定 RV32IM 指令子集的 CPU，在通过全部正确性验证的基础上，力争达到 100 分性能档位。**

项目由两人共同完成。我们需要交付可评测的 CPU，以及参数敏感度分析、架构设计探索两份报告。设计中应尽量真实地建模 CPU 的时序、资源限制和内存交互，使性能结果能够反映所实现硬件的行为。

**所有设计取舍，都以满足任务约束并提高可验证的性能为标准。** 可以自行添加 I-cache、D-cache，也可以探索更宽的发射、寄存器重命名、乱序执行等方案；是否采用，需要结合正确性、IPC、综合面积和时序结果判断。具体微架构在后续设计讨论中确定。

| 目标维度 | 本组目标 |
| --- | --- |
| 实现语言 | Chisel，生成可供 Yosys 和 Verilator 使用的 Verilog RTL |
| 指令支持 | 完成任务要求的 RV32IM 子集 |
| 功能正确性 | 通过基础程序和 CPU Simulator 中的要求程序 |
| 性能目标 | 在当前规则下冲刺 100 分：面积 ≤ 40,000、IPC ≥ 1.0140、频率 ≥ 300 MHz |
| 性能评测内存 | 统一内存，读写延迟按 20 周期建模 |
| 架构可配置性 | 对发射宽度、物理寄存器数量、ROB 条目数等适用参数进行参数化 |
| 设计依据 | 用正确性测试、仿真统计和综合／时序结果支撑设计选择 |

## 2. 指令集范围

目标指令集为 **RV32IM**：RV32I 是 32 位基础整数指令集，M 扩展提供整数乘除法指令。以下指令不作要求：

| 不作要求的类别 | 指令 |
| --- | --- |
| CSR 访问 | `CSR*` |
| 环境调用与断点 | `ECALL`、`EBREAK` |
| 内存与取指同步 | `FENCE`、`FENCE.I` |
| 字节／半字加载 | `LH`、`LHU`、`LB`、`LBU` |

**上述豁免不能扩展到未列出的指令。** 尤其需要注意：

- `LW` 仍在要求范围内；`SB`、`SH`、`SW` 没有被豁免，仍需支持。
- M 扩展不能只实现向量乘法用到的乘法，还需覆盖要求中的乘法高位、除法和取余等指令。
- 基础整数运算、逻辑运算、移位、比较、条件分支和跳转等，均需按要求实现。

后续实现时应建立逐条指令的支持清单与测试对应关系，避免仅凭几个程序运行成功就认定整个指令子集已经完成。

## 3. 正确性是获得后续分数的前提

| 阶段 | 要求 | 累计分数 |
| --- | --- | ---: |
| 基础程序 | 全部通过向量乘法、向量加法、0 到 100 的累加 | 75 |
| 仿真程序 | 在上一阶段基础上，继续通过 CPU Simulator 中的要求程序 | 85 |

**未通过前一阶段，不能获得后一阶段的分数。** 因此，性能优化必须建立在功能正确的实现上；修改微架构或参数后，也需要验证功能是否仍然正确。

基础程序用于建立最初的可运行版本，CPU Simulator 程序用于继续验收。性能评分使用的 BenchMark 与这些正确性阶段应分别记录结果。

## 4. 性能与面积评分目标（待定）

功能验证通过后进行性能评分，以 **Sodor 的顺序执行五级流水线 CPU** 作为 baseline。

| 评测项 | 当前要求 |
| --- | --- |
| 面积 | 使用 Yosys + ASAP7 综合评测 |
| IPC | 使用 Verilator 对 Verilog RTL 仿真统计，测试点为 BenchMark |
| 频率 | CPU 频率不得低于 300 MHz |
| 内存延迟 | 获取性能阶段分数时，内存读写延迟必须为 20 周期 |

在频率达标且满足前置验收要求的情况下，**面积和 IPC 必须同时满足同一档位的限制**：

| 性能阶段 | 最大面积 | 最低 IPC | 本阶段加分 | 累计分数 |
| --- | ---: | ---: | ---: | ---: |
| 1 | 10,000 | 0.6000 | +5 | 90 |
| 2 | 20,000 | 0.7800 | +5 | 95 |
| 3 | 40,000 | 1.0140 | +5 | 100 |

每通过一个性能阶段加 5 分，通过更高阶段会同时获得较低阶段的分数。相邻档位的设置规律为：IPC 门槛提高至 1.3 倍，面积上限提高至 2 倍。面积数值的单位与统计口径尚未在给定要求中说明，以正式评测为准。

**本组冲刺的目标组合是：全部功能验证通过 + 20 周期内存延迟 + 面积 ≤ 40,000 + IPC ≥ 1.0140 + 频率 ≥ 300 MHz。**

例如，面积为 30,000、IPC 为 0.90 时，虽然两项分别落在不同档位的范围内，但不满足任何一行的完整条件，不能获得性能阶段加分。设计时必须同时关注面积与 IPC。

300 MHz 对应约 3.33 ns 的时钟周期预算。IPC 由仿真统计得到，频率需要依据正式评测采用的时序方法验证；在测试平台中设置时钟周期本身不能证明硬件已满足频率要求。

## 5. 内存结构与延迟约束

### 5.1 一个统一内存

指令和数据访问采用**冯·诺依曼结构，只有一个统一内存**。允许自行添加 I-cache 和 D-cache，但二者最终仍连接到同一个统一内存。

下面展示的是允许探索的一种结构，Cache 是否采用、如何组织，需要通过评测决定：

```mermaid
flowchart LR
    F[CPU 取指路径] --> I[可选 I-cache]
    L[CPU 数据访存路径] --> D[可选 D-cache]
    I --> C[统一内存访问控制]
    D --> C
    C --> M[统一内存：指令与数据]
```

统一内存的端口数、请求吞吐率、允许的并发请求数等尚未给定。接口确认前，不应假定取指与数据访问可以无限并行。

### 5.2 两种内存延迟条件

| 使用场景 | 内存读取／写入延迟 |
| --- | ---: |
| 基础功能验证条件 | 3 周期 |
| 争取性能阶段分数 | 20 周期 |

本组以 100 分为目标，因此架构设计与性能优化必须面向 **20 周期内存延迟**。3 周期配置可用于功能验证，但其 IPC 不能代替性能评分要求下的结果。

内存访问延迟也不等于内存请求的发起间隔；后者需要依据正式接口确认。若采用 Cache，命中、缺失、填充、写入处理和访问冲突等行为都应落实到实际设计及仿真中。

### 5.3 面积计入规则

- 内存不会被 Yosys 综合，其面积不计入面积成绩。
- **不允许使用寄存器组冒充该内存。**
- Cache 的存储阵列、标签阵列及相关控制逻辑如何计入面积，给定要求尚未明确，需要根据评测规则确认；不能直接假定整个 Cache 都免费。

## 6. 本组的设计原则

| 原则 | 对具体工作的要求 |
| --- | --- |
| 正确性优先 | 每个优化版本都应保留正确性验证结果，性能提升必须建立在正确执行之上 |
| 以 100 分为目标 | 同时管理面积、IPC 和频率，面向 20 周期内存延迟进行设计 |
| 性能收益可验证 | 用相同测试集、内存条件和统计口径比较方案，记录收益及资源代价 |
| 尽量真实地模拟 CPU | 在 RTL 中体现流水线停顿、资源占用、数据依赖、控制流变化和访存等待等实际行为 |
| 按收益决定复杂度 | I-cache、D-cache、更宽发射和乱序执行等都是候选手段，依据实测结果与实现成本决定取舍 |
| 参数化贯穿设计 | 从模块接口和资源分配阶段考虑参数变化，保证不同受支持配置能够生成、运行和验证 |

在通常“完成指令数／周期数”的 IPC 定义下，每周期至多完成一条指令的设计无法达到 1.0140 的目标。因此，冲刺 100 分需要重点研究支持平均每周期完成超过一条指令的架构。最终采用怎样的发射、执行和提交宽度，以及是否采用乱序执行，要结合正式 IPC 统计口径和实验结果确定。

“尽量逼真”在本项目中的含义，是让仿真忠实体现所实现硬件的行为。设计复杂度的增加，需要服务于规定范围内的正确执行、性能提升或可信的性能分析。

## 7. 参数化与实验要求

最终设计应支持关键架构参数的配置，并分析性能对各参数的敏感度。

| 参数 | 含义 | 需要观察的结果 |
| --- | --- | --- |
| 发射宽度 | 每周期最多能够发射的指令数；具体阶段定义应在设计文档中统一 | 宽度变化对 IPC、面积和时序的影响 |
| 物理寄存器数量 | 采用寄存器重命名时，可分配的物理寄存器资源 | 寄存器资源不足造成的停顿及扩容收益 |
| ROB 条目数 | 采用 ROB 时，可跟踪的未提交指令数量 | 在途指令容量变化对 IPC 和资源占用的影响 |
| 其他实际采用的参数 | 例如 Cache 容量／相联度、队列深度、执行单元数量 | 对相应性能瓶颈的改善及面积、时序代价 |

物理寄存器和 ROB 的具体组织取决于最终架构；不能为了形式上的参数化设置不影响硬件行为的参数。若最终方案不采用这些结构，应在报告中解释架构选择及其与参数化要求的对应关系。

参数实验应记录完整配置，在统一条件下比较。分析单个参数时，尽量固定其他参数；必要时补充组合实验，解释资源之间的相互限制。每个受支持配置都应具有明确的合法范围，并通过相应的正确性检查。

## 8. 工具链与最终交付

课程允许 Verilog/SystemVerilog、Chisel、Assasyn 等实现语言，**本组明确使用 Chisel**。Yosys 的评测输入为 Verilog，因此必须打通以下流程：

```text
Chisel 源码与参数配置
        ↓ 生成
可供评测工具使用的 Verilog RTL
        ├─ Verilator：正确性仿真、BenchMark IPC 统计
        └─ Yosys + ASAP7：面积综合评测

频率是否达到 300 MHz：按正式评测规定的时序流程验证
```

最终提交 **CPU 和两份报告**：

| 交付物 | 应说明或包含的内容 |
| --- | --- |
| CPU | Chisel 源码、参数配置、可供 Yosys 和 Verilator 使用的 Verilog RTL，以及复现生成和评测所需的说明／脚本 |
| 报告一：参数敏感度分析 | 不同发射宽度、物理寄存器数量、ROB 大小等适用参数下的 IPC 变化；注明测试条件，并结合面积、时序和瓶颈解释结果 |
| 报告二：架构设计探索 | 探索过的方案、选择原因、实验对比、采用或放弃的依据，以及最终架构和仍存在的瓶颈 |

开发过程中应同步保存实验配置和结果，让最终报告能够追溯每项结论。

## 9. 推进顺序与需要确认的评测细节

项目按以下顺序推进；性能结构的规划和探索可在功能开发过程中同步开展：

1. **明确接口与测试条件**：落实指令支持清单、统一内存协议、测试程序和工具链。
2. **建立正确的可运行版本**：通过三项基础程序，再通过 CPU Simulator 中的要求程序。
3. **建立性能测量基准**：在 20 周期内存延迟下运行 BenchMark，记录 IPC、面积和频率结果。
4. **根据瓶颈改进架构**：比较候选方案，争取依次达到 90、95、100 分档位；每次优化后检查正确性。
5. **完成参数扫描与交付**：选定最终配置，整理 CPU、复现说明及两份报告。

以下细节尚未出现在给定材料中，应在对接评测环境时确认：

- 性能与面积评分表的正式版本，以及面积单位、综合配置和频率验证方法。
- CPU Simulator 和 BenchMark 的具体程序、入口、结束条件与版本。
- IPC 的计数事件、统计区间，以及多个测试点的汇总方式。
- 统一内存的端口、握手协议、请求吞吐率、并发能力，以及 3／20 周期延迟的精确定义。
- Cache 各部分的面积计入方式，以及程序装载、复位状态和其他必需接口约定。

这些信息会影响实现细节与实验结论。当前团队目标保持明确：**使用 Chisel，满足指定 RV32IM 子集和统一内存等约束，以可信的仿真和综合结果驱动设计，力争达到 100 分。**
